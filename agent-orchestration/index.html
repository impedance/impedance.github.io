Главный вывод

Оставь Issues. Урежь контракт. Добавь телеметрию.

GitHub официально закрепил Issue → agent → PR как стандарт: Agent HQ (Universe 2025), Copilot coding agent из коробки. Ближайшие зрелые аналоги твоего UAW-контракта — issue-orchestrator (bounded runs в worktrees с gates) и orchestrator-sh (Issues = backend, labels = статус).

Академические harness'ы (SWE-bench, SWE-EVO) показывают: решает не YAML-обёртка, а Outcome + machine-checkable Verification (fail-to-pass тесты). Телеметрия не зависит от формата постановки — она идёт из OTLP/hooks, а issue number это идеальный correlation ID.

01 · Твой контур сегодня

Как устроен pipeline

Contract

YAML task_contract v1: kind, profile, base SHA, publication (branch + draft PR), risk/protected, evidence. Пример — issue #191 в san-obsid.

Outcome + Scope

Проверяемый результат, exclusions, must-read файлы, allowed writes. Агент знает границы до старта.

Invariants

Pinned protocol agent-workflow v1, immutable _raw, запрет merge/visibility changes. Защита от агента-энтузиаста.

Verification

Run receipts, claim→source spot checks, frozen pass rule. Reviewer может принять честный negative report.

Почему Issues выигрывают

✓ Все топ-агенты читают Issues и открывают PR нативно; Copilot agent даёт issue→PR из коробки.

✓ 200+ issues — актив, переезд на Linear окупается только после ~300–500 тикетов.

✓ Langfuse/OTLP трейсинг не зависит от формата; issue number — готовый trace key + EXECUTOR RESULT как span.

Где боль Issues

× API latency ~1–2s и rate limits против zero-latency локального TASKS.md.

× YAML-обёртка избыточна: harness'ы доказывают, что решают Outcome + тесты.

× Нет checkpoint/resume для ночных прогонов — единственный доказанный пробел (Flow, AgentArch).

04 · Наука

Что говорит arXiv

Строгие контракты работают

Know-the-Ropes: fuzzy contracts убивают multi-agent gains — твой формальный контракт теоретически обоснован. AgentMesh (Planner→Coder→Debugger→Reviewer) — академический эквивалент Executor + Reviewer в UAW.

Но статики мало

Flow: workflow adjustment during execution важнее initial plan — статичный YAML недостаточен без replanning. SEW: self-evolving workflows бьют hand-crafted — следующий шаг: контракт, который агент сам улучшает.

AgentArch (18 конфигураций): «provably better format» не существует — только trade-offs по design dimensions. Поэтому ниже — не смена формата, а 6 точечных усилений твоего.
05 · Decision

План из 6 шагов

1. Оставить Issues primary queue

Мейнстрим, закреплённый Agent HQ. 200+ issues — актив. Переезд не окупается.

2. Ужать task_contract v1

Оставить 4 секции (Outcome / Scope / Invariants / Verification), YAML сделать опциональным. Пишут Outcome + тесты, а не схему.

3. TASKS.md как локальный mirror

Автогенерация из открытых Issues (gh issue list → TASKS.md) — агент на VDS работает без API-лагов, Issues остаются source of truth. Сниппет — ниже.

4. Не ставить beads

Выигрыш проявляется при ≥3 concurrent agents и long-horizon memory. Пересмотреть только при переходе к флоту.

5. Langfuse self-hosted на VDS

Один Docker. Issue number как trace tag, EXECUTOR RESULT как span. Собственные цифры latency / cost / success rate по типам задач — ответ на «provably better».

6. Checkpoint / resume для ночных прогонов

Run-state файл per issue (LangGraph-style или просто state.md) — pause / inspect / replay. Закрывает единственный доказанный пробел статичного контракта.
